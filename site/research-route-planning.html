I

Abstract

From a camera box to a route decision.

Standard Nav2 treats a corridor as geometry. This work closes the loop from what the robot sees to which route it chooses, in real time, on a CPU-only Raspberry Pi 5.

The paper introduces a computationally efficient semantic-aware route planning framework for indoor mobile robots. Monocular object detection is fused with 2D LiDAR range estimation, and the resulting semantic annotations feed the Nav2 Route Server for penalty-weighted route selection. Object localisation in the map frame uses Angular Sector Fusion (ASF), a deterministic geometric method that needs no parameter tuning: it projects YOLO bounding boxes onto LiDAR angular sectors and takes a 25th-percentile range, which stays robust to sparse returns and partial occlusions.

All intrinsic and extrinsic sensor parameters are resolved at runtime from ROS 2 topics and the URDF transform tree. Detected entities are classified by mobility (dynamic, static, minor), persisted in a GeoJSON semantic map and propagated to navigation-graph edges as additive penalties and velocity constraints. A reactive module watches semantic cost updates during execution and recomputes the route when a threshold is crossed.

Over 115 navigation legs on three heterogeneous robots, the system reached a 97% overall success rate (baseline 100%, adaptive 94%) with 42 replanning events in 57% of adaptive legs. Mean navigation time did not change significantly (Mann–Whitney p = 0.157), but its spread fell from σ = 31.1 s to 11.0 s, mainly by avoiding AMCL recovery outliers. YOLO26n ran at 5.5 ± 0.7 FPS through NCNN, and offloading inference cut CPU load from 85% to 48%.

IV

Method

A semantic layer that leaves Nav2 alone.

A.Three Xplorer robots, one Raspberry Pi 5 each

Experiments ran on three in-house, four-wheel differential robots, Xplorer-A, B and C, designed and built within the university's robotics teams. Each runs an author-developed ROS 2 baseline (ros2_control hardware interface, odometry, IMU and LiDAR integration, state estimation), so differences between baseline and adaptive runs come from the semantic routing layer, not from hidden software changes.

All computation runs on a Raspberry Pi 5 (16 GB, Cortex-A76, no GPU or NPU) with a Logitech C920 at 640 × 480, an STL-19P 2D LiDAR (360°, ≈503 rays, 10 Hz) and a BNO055 IMU. The stack is ROS 2 Jazzy with Nav2 1.3.10: AMCL, an EKF at 20 Hz, MPPI at 20 Hz and SmacPlannerHybrid. Xplorer-C splits compute across two RPi 5 boards over Ethernet, with the detector alone on the second board.

B.Angular Sector Fusion, step by step

ASF hardcodes nothing. Focal length and principal point come from the first CameraInfo message (fx = 687.54 px, cx = 308.11 px for the C920), scan geometry from the first LaserScan (503 rays at 0.716°), and every frame relation from TF2. Moving the pipeline to a new robot needs only standard topics and a valid URDF; the paper confirmed identical behaviour on all three robots.

  1. Box → anglesPinhole model turns xmin, xmax into θleft, θright.
  2. Angles → sectorSign flip plus a yaw offset maps them onto LiDAR ray indices.
  3. Sector → range25th percentile of valid returns; at least two rays required.
  4. Polar → pointRange and sector centre become x, y in the laser frame.
  5. Laser → mapTF2 chain base_laser → base_link → odom → map, queried at time zero.
  6. TrackMatch by class within 0.5 m, median of the last 5 positions.
# Step 1, camera angles from the box edges (runtime f_x, c_x) θ_left = atan2(x_min − c_x, f_x) θ_right = atan2(x_max − c_x, f_x) # Step 3, the nearest consistent surface in the sector is most likely the object d = percentile_25(valid_ranges) # mean or median would let the far wall leak in

C.A semantic map that remembers what moves

Localised objects go into a persistent store serialised as a GeoJSON FeatureCollection (semantic_objects.geojson), readable in QGIS and recoverable after restarts. Each class carries a mobility category that decides how much it matters to routing and how long it is remembered. Static and minor objects are refined with an exponential moving average (α = 0.7); people are simply overwritten, because they move.

A cleanup timer removes expired objects every 10 s, and the graph annotations follow at the next save, so a corridor clears itself when a person walks away.

D.From objects to edge penalties to a new route

Every object within 1.5 m of a graph edge contributes to that edge's penalty, scaled by how close it is and how confident the detector was. The Route Server then scores edges with a DistanceScorer (weight 1.0) and a PenaltyScorer (weight 5.0); the 5:1 ratio makes semantics dominate when objects are present. A person near an edge adds roughly 25–40 penalty, 125–200 weighted cost units, against 1–3 units for a 1–2 m edge.

penalty_edge = Σ_i P_base(mobility_i) × proximity_factor_i × confidence_i proximity_factor = max(0.1, 1.0 − d_object_to_edge / d_proximity) # d_proximity = 1.5 m speed_limit_edge = min_i S(mobility_i) # 30 %, 60 % or 90 %

Adaptive navigation starts with a prescan: two 180° spins (about 10 s), a 35 s wait while the pipeline annotates the graph, an explicit set_route_graph reload and a heading realignment. Navigation then loops: ComputeRoute from the current AMCL pose, path-gap correction if needed, FollowPath with MPPI, and a penalty check every 2 s. A change above δ = 2.0 on any active edge cancels FollowPath and replans; if route planning fails entirely, the robot falls back to NavigateToPose.

Notes for Nav2 users. Route Server 1.3.10 accepts only scalar numeric edge metadata, so the system writes two graphs: a rich diagnostic one and a stripped Nav2-safe one. ComputeRoute needs use_start = True with an explicit AMCL pose after any reinitialisation. When the dense path starts more than 1 m from the robot, waypoints are prepended every 0.15 m, otherwise MPPI reports success without moving.

V

Results

Not faster on average. Far more predictable.

A controlled ablation with repeated measures: the only manipulation is the navigation mode, repeated across robots and sessions. 115 legs were collected (45 baseline, 70 adaptive) over 27 sessions, and 111 met the validation criteria (goal reached, ≥ 1 m travelled, XY error ≤ 2 m, duration ≥ 3 s). A.Navigation time: the spread collapses

Forward legs took 37.3 ± 31.1 s in the baseline and 32.5 ± 11.0 s adaptive; the medians are close (25.4 s vs 29.8 s). Both distributions are non-normal (Shapiro–Wilk p < 0.005), so the comparison is non-parametric: no significant difference in central tendency, and a marginally significant drop in dispersion. Two baseline runs of 97.4 s and 142.0 s came from AMCL recovery cycles stalling the free-space planner. No adaptive run exceeded 62 s.

The paper is explicit that the adaptive mode was not designed to be faster, but more predictable. The variance reduction held on all three robots and in both leg directions.

On a clean graph the Route Server always chose the direct route at cost 5.7. With semantic penalties the same start–goal pair cost 42 to 107, and routes through nodes 3 or 5 appeared. Many replans truncated the route, (0, 2, 7) → (2, 7), rather than switching it, which the paper attributes to the small graph. No route through the lower nodes 4 and 6 was ever selected.

C.What the robots saw

Across all adaptive sessions ASF recorded nine object classes. People were detected on all three robots: real passers-by, not staged actors. The minimum distance between trajectory and nearest semantic object was 0.4 ± 0.8 m baseline and 0.3 ± 0.3 m adaptive; the paper reads this carefully: in a 5.7 m graph every route passes within the 1.5 m proximity radius of something, so the benefit shows up at route level, not centimetres.

VI

Limitations and future work

What it does not prove yet.

Limitations, as the paper states them

  • The 2D LiDAR plane. With the scanner about 16 cm above the floor, wall-mounted or elevated objects get no range return and are filtered out.
  • Prescan overhead. A narrow ≈50° camera needs a 360° prescan; the 35 s wait plus ≈11 s rotation make an adaptive forward leg ≈79 s wall-clock against 37.3 s baseline. Best for semi-static spaces.
  • A small graph. 7 nodes over ≈5.7 m limits route diversity: the direct route won 52% of forward legs, and the lower route never appeared.
  • No centimetre gain. Minimum object distance did not improve (0.3 vs 0.4 m); the benefit is at route level.
  • Localisation is the real bottleneck. All four failures were AMCL drift on Xplorer-B, and object positions inherit any map→odom error.
  • One corridor, no external ground truth for object positions; residual within-session correlation is possible.

Future work

  • Harder environments: people deliberately entering routes to force full route switches; multi-room offices, open-plan spaces with movable furniture, warehouse-like narrow aisles.
  • Bigger graphs: a 20–30 node graph across FIIR corridors (≈40 m path), then a full-floor graph with 50+ nodes and ≈200 m of path.
  • 3D depth sensing (for example a RealSense D435i) to localise elevated and wall-mounted objects.
  • Continuous, incremental graph updates during navigation, removing the dedicated scan-and-wait phase.
  • Mixed-effects statistics with robot and session as random factors, and motion capture for object ground truth.
